# evo-worker

Stateless worker evaluating decoder and strategy genomes pulled from the `JOBS_EVO` NATS work queue (`jobs.evo.>`).

**Status:** evaluates `evo.eval.decoder` jobs end to end with baseline CPU decoders on **VictoriaMetrics data** (`fa_trade_price` via `fa-tsdb`, in-memory `md.trade.>` buffer as fallback) — genome parsing, point-in-time CRPS/coverage/trading-value scoring, multi-objective `JobResult` (JSON + typed `objectives`/`directions` maps), optional `latent.state.>` conditioning of the retrieval decoder, `JobProgress`, GPU-arbiter lease with preemption handling, `DecoderOutput` publishing, eval report persistence to Garage (`fa-artifacts/evals/<generation>/<job>.json`) when credentials are configured. Handles **`evo.vary.decoder`** jobs (next-population variation with `fa-evolution`, lineage to Helix). **Strategies (D-052):** `evo.eval.strategy` replays a GP strategy genome through `fa_backtest::replay` on VictoriaMetrics bars net of the shared cost model (`go/services/broker-gateway/costs.yaml`), `evo.vary.strategy` breeds the next population with `fa_strategies::ops`. Every evaluation (decoder or strategy) is written to the Postgres **trial registry** (`validation.trial`) and the generation's deflated Sharpe / PBO (`validation.generation_stats`) are recomputed and returned in the result (`generation_stats`). Other job kinds get `STATUS_FAILED` ("not implemented").

## What it does per job
1. Decodes `Job`; genome = `Job.spec` if present, else `Job.genome_id`. The spec is either the genome itself (kv or JSON, D-044) or an envelope `{"genome": "...", "data_window": {"hours": 6}}` / `{"data_window": {"start_ms", "end_ms"}}` (the orchestrator sends the envelope when `data_window_hours` was given). Format: [`crates/fa-decoders/README.md`](../../crates/fa-decoders/README.md) (`forecast:h=5;lb=32;…`, `retrieval:k=20;tau=30;…`, or a bare id that is hash-derived). Separate genes with `;`, never `,`.
2. Acquires a GPU lease from the arbiter (`ctl.gpu.acquire`, class `evolution_eval`, `--gpu-lease-mb`, default 512; `0` disables). Queued leases wait for `ctl.gpu.granted` until the job deadline; an unreachable arbiter is tolerated (CPU work).
3. Loads the evaluation window (see *Evaluation data*): `fa_tsdb::Tsdb::trade_prices` for every instrument (or the genome's `inst`) at the genome's timescale step, else the buffer. Builds the decoder with the latest `latent.state.>` context (`fa_decoders::baseline::build_with`) and runs `fa_backtest::eval::evaluate`: forecast at every step using only past data (and latents as of that step), scored against the realised horizon return. Stops at `budget_gpu_ms` (partial evaluation, `budget.truncated=true`), on `ctl.gpu.preempt` for its lease (→ `STATUS_PREEMPTED` with `checkpoint_ref`; redelivered jobs re-evaluate from scratch because evaluation is cheap) or when the window is exhausted.
4. Publishes `JobProgress` on `jobs.progress.<job_id>` every 500 ms, in-progress JetStream acks every 20 s (`ack_wait` 60 s, `max_deliver` 5), one message in flight per worker.
5. Publishes `DecoderOutput` on `decoder.output.rnn_prior` (forecast quantiles) / `decoder.output.retrieval` (analogs with similarity, window end, time distance) for up to 4 instruments, then the `JobResult` on `jobs.result.evo.eval.decoder`, then acks. If the result cannot be published the message is left unacked for redelivery.

### Result payload (`evo.eval.decoder/v0`, D-025 compatible)
```json
{"protocol":"evo.eval.decoder/v0","score":0.39,
 "objectives":{"crps":6e-4,"crps_skill":0.39,"coverage":0.94,"coverage_err":0.04,"hit_rate":0.56,
               "trade_sharpe":0.13,"trade_psr":0.69,"compute_cost":2.5,"n_eval":18},
 "directions":{"crps":"min","crps_skill":"max","coverage_err":"min","hit_rate":"max","trade_sharpe":"max","trade_psr":"max","compute_cost":"min"},
 "genome":{...},
 "data":{"source":"victoriametrics","timescale":"1s","step_ms":1000,"window_start_ms":..,"window_end_ms":..,"vm_url":"http://127.0.0.1:8428",
         "vm_series":1,"vm_error":null,"latents":{"instruments":1,"points":195},"instruments":[{"instrument_id":"0190…0001","venue":"sim","n_steps":4254,"n_eval":4232,...}]},
 "budget":{"budget_ms":2000,"elapsed_ms":11,"truncated":false},"stop":"complete",
 "report_ref":{"planned":"fa-artifacts/evals/<generation>/<job>.json","persisted":true}}
```
`score` = `crps_skill` (the scalar fallback); the orchestrator ranks with NSGA-II over `objectives`/`directions`, which the worker also sets as the typed `JobResult.objectives` / `JobResult.directions` proto maps. control-api shows `objectives` in the Evolution Lab. Objective definitions: `crates/fa-backtest/src/eval.rs`. `data.source` is `victoriametrics` or `md.trade.> in-memory buffer (fallback: <reason>)`.

### `evo.vary.decoder` (next population)
`Job.spec` = `{"parents": [{"genome": "...", "objectives": {...}, "directions": {...}} | "genome string", ...], "n_children": 3, "seed": 7, "generation": 1, "budget": {"total_gpu_ms", "min_budget_gpu_ms", "eta", "rungs"}?}` (parents best first). The worker parses each parent (`DecoderGenome`), maps the numeric genes to `fa_evolution::Genome.params`, runs `fa_evolution::vary::vary` (same-family uniform crossover with p = 0.5, Gaussian mutation σ = 0.2 relative; overridable with `sigma` / `crossover_prob`), clamps the children back with `with_params` and returns them as canonical kv strings, de-duplicated against the parents. `n_children = 0` with `budget` sizes the population with `fa_evolution::plan_halving` (spec 34 §6.4): `children = initial_candidates − parents`. Result: `{"protocol":"evo.vary.decoder/v0","children":[...],"n_parents","n_children","plan"?,"lineage":[{"child","parents","op"}],"helix":{"persisted",...}}`. Lineage goes to Helix best effort (`upsert_genome` for parents and children, `link_parent` edges, `add_fitness_record` with the parents' objectives; `FA_HELIX_URL` or `[helix] url`); failures only warn. No GPU lease is taken.

### `evo.eval.strategy` (strategy replay, spec 35 §6.1–6.2)
`Job.spec` = the genome text (`fa_strategies::genome::StrategyGenome` inline TOML: `{ id = "gp-…", timescale = "1s", steps = 5, lookback_bars = 32, signal = "(mul 400 analog_forecast)", uncertainty = "region_entropy" }`) or the envelope `{"genome": "<text>", "data_window": {...}, "generation": n, "rung": r, "purpose": "selection"|"diagnostic"}` the orchestrator sends. The worker loads bars at the genome's timescale for every instrument in the window (`data::load_bars`; same VM / buffer rules as decoders), reads the locked holdouts of that timescale and the generation's trial count / Sharpe variance from the registry, loads the **recorded latents** of the window (below) and runs `fa_backtest::replay::PipelineReplay` (capital 100 000 EUR, cost model from `--costs` / `FA_COSTS`, default `go/services/broker-gateway/costs.yaml`, built-in defaults when missing). A Selection replay whose window intersects a holdout is **rejected** (`STATUS_FAILED`, error `rejected: selection window intersects …`), never scored; `"purpose": "promotion"` is rejected too (`rejected: promotion replays run only as evo.eval.strategy.holdout …`). Nothing is published on `signal.*`.

**Recorded latents (D-059, `recorded.rs`).** Before the replay the worker reads the `LATENT` JetStream stream by time (`fa_bus::replay::read_latents`: `latent.state.>`, `latent.region.>`, `latent.transition.>`, `decoder.output.>` over `[window start − preload, window end]`, preload `FA_EVO_LATENT_PRELOAD_HOURS`, default 1) into `fa_backtest::latents::RecordedLatents`, cached per `(window, timescale, instrument set)` in a bounded `LatentCache` (8 windows). The replay feeds them point-in-time into the same `LatentGraph` / `DecoderOutputs` the live `strategy-runtime` uses, so graph and decoder primitives answer from what the live strategies saw; windows before the recordings fall back to prices. Latents of another snapshot than `Job.snapshot_id` are refused (`rejected: latents of snapshot(s) …`) unless the purpose is `diagnostic`. `FA_EVO_NO_LATENTS=1` disables the feed, `FA_EVO_LATENT_MAX_MESSAGES` caps a read (default 500 000 per filter). An unreadable stream only warns (`latents.error`) and the replay runs fallback-only.

Result (`evo.eval.strategy/v0`): `score` = `deflated_sharpe`; `objectives` / `directions` = `deflated_sharpe` max, `sharpe` max, `max_drawdown` min, `turnover` min, `cost_sensitivity` min, `compute_cost` min (+ informational `calibration`, `cost_share`, `psr`, `n_trades`, `n_obs`, `sources.graph`, `sources.decoder`, `sources.fallback` — primitive calls answered by the recorded graph, the recorded decoder outputs or the price fallback); `genome {text, id, …}`, `replay {purpose, window, cost_model, n_trials, trial_sharpe_var, instruments, n_steps, n_trades, gross_pnl, total_cost, net_pnl, snapshot, sources, latents{available, recorded, fed{states, regions, transitions, decoder_outputs}, snapshot{declared, seen, mixed}, graph_rows}, …}`, `latents {source, cached, summary, cache{hits, misses, windows}, error}`, `data`, `generation_stats`, `helix`, `report_ref`. The Garage report additionally holds `equity`, `returns` and the per-trade log `trades`. Each evaluated strategy is upserted to Helix as a `Genome` (kind `strategy`, family `gp`, params = text) with a `FitnessRecord` of its objectives.

### `evo.eval.strategy.holdout` (promotion replay on a locked holdout, spec 41 §6.4, D-059)
The **only** job that runs a `ReplayPurpose::Promotion` replay. `Job.spec` = `{"candidate": "<genome text or gp-… id>", "holdout_id": "<validation.holdout.id>", "snapshot"?: "…"}`; the control-api builds it from `POST /api/validation/holdout/{id}/evaluate` and publishes it on `jobs.evo.eval.strategy.holdout` (captured by `JOBS_EVO`). The worker needs the registry: it loads the holdout row by id (`rejected: holdout … is not locked` otherwise), resolves a `gp-…` id to the latest genome text evaluated under it, refuses a candidate of another timescale, replays exactly the holdout window `[start, end]` with the recorded latents and writes one `validation.trial` row with `kind = holdout`, `holdout_id` set and `generation = Job.parent_job_id` (`holdout-<id>` from the API). Holdout rows **never** feed selection: `TrialStore::trials` excludes them from the deflated-Sharpe / PBO inputs, no `generation_stats` row is touched (`generation_stats: null` in the result) and `GET /api/validation/reports/{candidate}` lists them separately under `holdout`. Result protocol `evo.eval.strategy.holdout/v0` = the strategy payload plus `holdout {id, timescale, start_ms, end_ms, locked_at_ms, note}` and `trial {kind: "holdout", recorded}`.

**Locking the first holdout** (nothing is seeded): pick a *completed* segment of the timescale that the recordings cover (`cargo run -p fa-bus --example read_range -- LATENT 'latent.state.1s.>' -7d now --limit 1` shows the oldest latent), then `curl -X POST http://127.0.0.1:7700/api/validation/holdout -H 'content-type: application/json' -d '{"timescale":"1s","start":"2026-11-10T04:36:00Z","end":"2026-11-10T04:56:00Z","note":"first 1s holdout"}'` → `201 {holdout: {id, …}}`; an overlapping lock of the same timescale answers `409`, a range ending in the future `400`. The row is immutable (trigger); re-lock by inserting a new, non-overlapping range. Mind spec 41 §6.4: Selection replays whose data window touches the holdout are rejected from then on, so lock a segment older than the selection windows you intend to use (`data_window_hours`), with an embargo gap. Then `curl -X POST http://127.0.0.1:7700/api/validation/holdout/<id>/evaluate -d '{"candidate":"gp-…"}'` and read `GET /api/validation/reports/gp-… → holdout`.

### `evo.vary.strategy`
Same request shape as `evo.vary.decoder` (parents = genome texts best first, `n_children`, `seed`, `generation`, `budget`?) plus `immigrant_frac` (default 0.1), `max_depth`, `max_nodes`. Children come from `fa_evolution::vary::vary_with` with `fa_strategies::ops` (subtree crossover between parents of the same timescale with p = `crossover_prob`, then point / subtree / hoist mutation, constant jitter or a spec-gene mutation) plus random immigrants (`fa_strategies::random`), de-duplicated by genome id; result `{"protocol":"evo.vary.strategy/v0","children":[texts],"child_ids","immigrants","lineage":[{child, parents, op}],"helix":{…}}`. Lineage to Helix as for decoders.

### Trial registry and generation statistics (spec 41 §6.5)
With Postgres reachable (`[postgres] url`, `--no-registry` disables) the worker inserts one `validation.trial` row per finished evaluation (holdout evaluations carry `kind = holdout` + `holdout_id` and are excluded from everything below) — generation id (`Job.parent_job_id`), loop index and rung (from the envelope), candidate text, kind, window, per-step Sharpe, `n_obs`, objectives and the per-step returns compressed into 64 block sums — then recomputes `fa_backtest::validation::generation_stats` over the generation's trials (deflated Sharpe of the best trial against the expected max of `n_trials`, PBO by CSCV with 16 blocks) and upserts `validation.generation_stats`. The stats ride in the result JSON as `generation_stats`; the orchestrator publishes the latest one in `generation.summary.validation`. The next strategy evaluation of the same generation uses `n_trials + 1` and the Sharpe variance for its own `deflated_sharpe` objective. Live round trip: `FA_PG_TEST=1 cargo test -p evo-worker`.

### Report persistence
At startup the worker loads `config/secrets.toml` (`$FA_SECRETS`; `FA_GARAGE_ACCESS_KEY_ID` / `FA_GARAGE_SECRET_ACCESS_KEY` override, D-020) and builds an `fa_blob::S3BlobStore` against `[garage] endpoint` of the platform config. Every OK result's JSON (pretty-printed, `application/json`) is then written to `report_ref.planned` and the published result says `"persisted": true`. Without credentials the worker logs one warning at startup and results carry `"persisted": false`; a failed write is a warning too and never fails the job. Create the key with `docker/garage-init.sh` and paste it into `config/secrets.toml` `[garage]`.

## Evaluation data
**Primary: VictoriaMetrics** (`[victoriametrics] url` of the platform config, `FA_VM_URL` override, `--no-tsdb` disables). `fa_tsdb::Tsdb::trade_prices` reads `last_over_time(fa_trade_price{inst=…}[step])` over the data window — the job's `data_window`, else `--data-window-hours` / `FA_EVO_DATA_WINDOW_HOURS` (default 6 h) ending now — at the genome's timescale step (`inst` label = UUID without dashes, as the ingestor writes it, D-038). The window is shrunk to ≤ 20 000 steps (VM's per-series point limit). A genome needs `warmup + horizon + 1` steps (forecast: `lb + 2h + 1`; retrieval: `2·lb + gap + 2h + 3`).

**Fallback: in-memory buffer.** The worker still subscribes to `md.trade.>` (last 50 000 trades per instrument, 64 instruments). When VM is unreachable, errors, or no series in the window is long enough, the buffer is used and `data.source` says `md.trade.> in-memory buffer (fallback: <reason>)`; a job only fails when both sources are too short (the error lists the VM error and buffer size).

**Latent conditioning.** The worker subscribes to `latent.state.>` and keeps the latest 20 000 `LatentState`s per instrument (concatenated expert means). Each eval job gets a snapshot as `DecodeCtx`; the retrieval decoder adds `lat · cos(latent as of query, latent as of candidate)` to its similarity (gene `lat`, default 0.5) whenever both latents exist — looked up as of each window end, so it stays point-in-time and deterministic. `data.latents` reports how many latents were available; heartbeat counters `latents.instruments` / `latents.points`.

## Run
```sh
cargo run -p evo-worker                # host, against compose NATS + VM; FA_CONFIG=config/platform.toml
cargo run -p evo-worker -- --gpu-lease-mb 0 --data-window-hours 2
# then start a generation through control-api (max_generations > 1 loops halving → variation → halving):
curl -X POST http://127.0.0.1:7700/api/evolution/generations -H 'content-type: application/json' \
  -d '{"kind":"evo.eval.decoder","snapshot_id":"snap-test","genomes":["forecast:h=3;lb=16","retrieval:h=3;lb=8;k=10","g1"],"eta":2,"min_budget_ms":2000}'
# strategies: genomes are strategies.toml inline tables (fa_strategies::genome), one per list entry
curl -X POST http://127.0.0.1:7700/api/evolution/generations -H 'content-type: application/json' \
  -d '{"kind":"evo.eval.strategy","snapshot_id":"snap-test","max_generations":2,"eta":2,"min_budget_ms":5000,
       "genomes":["{ id = \"a\", timescale = \"1s\", steps = 5, lookback_bars = 32, signal = \"(mul 400 analog_forecast)\" }",
                  "{ id = \"b\", timescale = \"1s\", steps = 10, lookback_bars = 64, signal = \"(mul 4 (sub (path_up 3) 0.5))\", uncertainty = \"(sub 1 stay_prob)\" }"]}'
curl http://127.0.0.1:7700/api/evolution/jobs ; curl http://127.0.0.1:7700/api/evolution/populations
```
Only one consumer may read a work queue, so stop the compose `evo-worker` (`docker compose stop evo-worker`) when running one on the host, or they compete for jobs.
